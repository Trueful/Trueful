# Threat Model

## Threats and Main Countermeasures

| Threat | Main Countermeasure |
|---|---|
| Malicious website | Security Profile (Production = strict), session partition isolation, Tier B/C gates, visualization via the CSP parser |
| Malicious Plugin | Worker Thread execution (no network/filesystem/direct IPC access), independent Tier recalculation by Main Process, mismatched return schemas are rejected |
| Prompt injection (AI manipulation via malicious DOM content) | The existing invariant that Main Process always independently re-verifies the tier/sideEffectConfidence generated by AI is itself the countermeasure. The design principle of never trusting AI output covers both Plugin defense and prompt-injection defense |
| Tampered Workspace file | Imported Workspace manifests are forced into the most restrictive SecurityProfile (development) by default, and the declared contents of `securityProfile`/`testTargets` are never trusted as-is. The Pattern Trust Ledger is never bundled in the first place |
| Local information leakage | Credentials are delegated to the OS keychain (no plaintext self-storage), reasonLog discloses only counts/categories across Workspaces, and Cookie values/passwords are never logged |

## Assets

| Asset | Description |
|---|---|
| Password / Credential | Stored in the OS keychain via safeStorage |
| Session Cookie | Isolated in a per-Workspace session partition |
| Workspace Manifest | The project definition itself |
| Pattern Trust Ledger | Trust track record of inspection executions |

The overall threat model is these Assets crossed with the Attackers above.

## Authentication & Password Storage

No custom encryption is built; delegated to the OS-standard credential store (Windows Credential Manager / macOS Keychain / libsecret) via Electron's safeStorage API. A direct application of Local First (#11): an OS implementation has a smaller attack surface than custom crypto.

## SQLite Encryption (Not Adopted — Rationale)

Full encryption of history/manifest via sqlcipher etc. is not done. Credentials are already protected by safeStorage (OS keychain). History/manifest are delegated to OS-level disk encryption (BitLocker/FileVault etc.); no custom encryption layer is added — the same pattern as prioritizing OS implementation over custom crypto (identical to the credential storage decision). The premise that OS-level protection is the primary line of defense against malware reading data under the same user privileges is explicitly accepted.

## Handling of the file:// Protocol

Local HTML files are not treated as a trusted domain; like imported Workspaces, they're treated as an "unknown origin." Permissions such as AI access are never elevated just because it's file://.

## Clipboard Permissions

JS-based clipboard read/write from web pages is blocked by default in Production/Development. Only relaxed in Testing/Custom (Strict is the default even for a developer tool).

## Handling of localhost

localhost/127.0.0.1 is included under the existing Development profile's "allow self-signed certificates" scope. However, this never bypasses the Tier B/C gate decision itself — certificate/CORS relaxation and Tier decisions are separate axes.
