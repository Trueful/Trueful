# Resolved Tensions（解消された内部緊張）

以降の全設計判断は、以下4つの解決パターンの応用でしかない。

| 緊張 | 解決パターン |
|---|---|
| Everything Configurable vs Zero Noise | 直交する軸として分離：設定できる（能力）／デフォルトで見える（表示）は別問題 |
| Predictable vs Never Get Lost | 提示と実行を分離：案内は自由、実行は同意が必要 |
| Security Is a Choice vs モード見失い | Transparencyを拡張し、モードを常時可視化（Ambient Indicator） |
| Local First vs Time First | Layerで裁定。ローカルはデフォルト、クラウドは透明性を伴う明示的opt-in |

## 緊張1：Everything Configurable（#6）vs Zero Noise（#14）

**問題**：「設定できないものは存在しない」を突き詰めると、設定項目自体が「不要な情報」としてノイズになる。

**解決**：Configurability と Noise は同じ軸の両端ではなく、直交する別の軸である。

| 軸 | 意味 |
|---|---|
| Configurable | 存在する自由度（バックエンドの能力） |
| Noise | デフォルトで見える情報量（フロントエンドの表示） |

**改訂ルール**：「設定できないものは存在しない。しかし、デフォルトで見えている必要はない。」
すべての設定はデフォルトで折りたたまれ、明示的な階層アクセス／検索でのみ到達する。

## 緊張2：Predictable（#8）vs Never Get Lost（#3）

**問題**：「次に見るべきページが分かる」ように案内することと、「勝手に動かない」ことは、能動性の度合いで衝突する。

**解決**：「提示（Suggest）」と「実行（Execute）」を明確に分離する。

- 提示：ブラウザは次の候補を常に示してよい（ハイライト、サイドパネル、ショートカット候補）
- 実行：遷移・送信・変更は必ずユーザーの明示的操作を要する

**改訂ルール**：「案内は自由、実行は同意が必要。」AIやブラウザの判断は常に inert（不活性）な提案として提示され、ユーザーの操作なしに状態を変えない。

## 緊張3：Security Is a Choice（#7）vs モード見失いリスク

**問題**：用途ごとにセキュリティレベルを変えられる自由は、「今どのモードで動いているか分からなくなる」事故を招く。

**解決**：Transparency（#9）の対象に「現在のセキュリティ／実行モード」を常時可視化項目として追加する。オンデマンドで説明できるだけでは不十分で、常設のアンビエントUI表示を必須とする。

**改訂ルール**：「モードは切り替えられる。ただし、切り替わった瞬間は常に見える。」

## 緊張4：Local First（#11）vs Developer First / Time First（#1, #19）

**問題**：ローカル優先を絶対化すると、クラウドの方が明らかに開発者の時間を節約する場面で足枷になる。

**解決**：Layer構造そのものが解決する。Local First は Layer 2（技術的自由度）に属し、Layer 0（Time First）に劣後する。ただし「劣後する」は「無視してよい」ではなく、Transparency（Layer 1）を経由する。

**改訂ルール**：「ローカルはデフォルト。クラウドは、透明性を伴う明示的な選択として許可される。サイレントなクラウドフォールバックは禁止。」
